# バックエンド実装の基準

## API 契約
- エンドポイント・リクエスト・レスポンス・エラー形式を先に決め、既存 API の命名と形式に合わせる。
- 既存の API を変更する場合は後方互換を保つ。保てない場合は報告の `unresolved` に書く。
- フロントエンドを別の implement が並列で実装する場合、決めた契約を報告の `summary` に明記する。

## データ
- スキーマ変更はマイグレーションで行い、ロールバック可能にする。
- 複数の書き込みが整合性を要する場合はトランザクションで囲む。
- 一覧取得は件数の上限またはページングを設ける。

## エラー処理
- 外部入力は境界で検証し、失敗時はクライアントが原因を判別できるエラーを返す。
- 例外を握りつぶさない。ログには原因を追える情報を残し、秘密情報・個人情報は出さない。

## テスト
- 受け入れ基準ごとに、正常系と主要な異常系のテストを書く。
- 外部サービスはテストで差し替え、テストが外部に依存しないようにする。

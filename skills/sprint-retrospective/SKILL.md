# スプリントレトロスペクティブ

## 原則
- スプリントに参加した全メンバー（起動された Agent の種類すべてと、スクラムマスター）が、それぞれ KPT を出す。スクラムマスターだけで済ませない。
- 感想ではなく、記録と指標を根拠にする。根拠の無い Keep・Problem は採らない。
- Problem は症状で止めず、根本原因まで掘り下げる。Try は根本原因を取り除くものにする。
- Try は5W1H と効果の確認方法をすべて埋める。1つでも欠けた Try は出さない。
- PO の承認は求めない。DoD の変更は案として残し、次のスプリント計画で PO に諮る。
- 各書式は [formats.md](formats.md) に従う。

## 手順
1. **指標の集計**
   - スプリントファイルの「記録」と「Agent 実行ログ」から、formats.md の指標を集計する。
   - `.scrum/metrics.md` に1行追記する。ファイルが無ければ作る。
   - 前のスプリントの行と比べ、大きく変わった指標を挙げる。
2. **前回の Try の効果確認**
   - `.scrum/agreements.md` の各項目について、「効果の確認」に書いた指標を今回の値で判定する。判定は `効果あり` / `効果なし` / `判定不能` とする。
   - `効果なし` の項目は、根本原因の見立てが誤っていたとみなし、手順4で再分析の対象にする。
   - 3スプリント以上、関係する事象が起きていない項目は削除候補にする。
3. **各メンバーの KPT**
   - `.scrum/team.md` の Agent のうち、このスプリントで起動されたものを1つずつ、「振り返りのみ」の依頼で並列に起動する。isolation は指定しない。
   - 依頼には formats.md の「メンバーへの依頼」の内容をすべて含める。
   - スクラムマスターも同じ書式で自分の KPT を書く。観点は進行、依頼の出し方、計画の精度である。
4. **統合と根本原因分析**
   - Keep：全員の Keep をまとめ、続ける理由を1文で添える。
   - Problem：同じ事象をまとめる。1回だけ起きた事象も対象にする。
   - スプリントファイルの「デモの判定」に差し戻しがあれば、必ず Problem に含める。指摘の区分（作り損ね・基準の書き漏れ・対象外）ごとに、なぜリハーサルやレビューで見つけられなかったかを分析する。
   - 各 Problem について、formats.md の「根本原因分析」に従ってなぜなぜ分析を行う。メンバーの分析は材料として使い、結論はスクラムマスターが出す。
5. **Try の選定**
   - 根本原因ごとに Try を作り、formats.md の「出口の選び方」で行き先を決める。
   - 1スプリントで採る Try は最大3件とする。指標への影響が大きい順に選ぶ。
   - 採らなかった Problem は、スプリントファイルに「未対応」として根本原因とともに残す。
6. **反映**
   - チーム合意：`.scrum/agreements.md` に formats.md の書式で追記・書き換え・削除する。
   - DoD 変更案：`.scrum/config.md` の `## DoD 変更案` 節に追記する。
   - チーム編成の変更案：`.scrum/team.md` の `## 変更案` 節に、追加・交代・削除する枠と Agent の候補、理由を追記する。
   - 改善 PBI：`backlog-operations` の `create` で `new` の PBI を作り、`comment` に `retro: Sprint <N>` と根本原因を書く。
   - plugin への改善提案：`.scrum/plugin-feedback.md` に追記する。
   - 容量：変更案を報告に含める。
7. **記録と報告**
   - スプリントファイルの末尾に、formats.md の「スプリントファイルへの記録」の書式で書く。
   - `phase` を `closed` にし、`- closed: <`date -Iseconds` の出力>` を `phase` の行の下に書き、`.scrum/` を `base_branch` にコミットする。
   - PO に、指標の要点、各 Try（行き先を含む）、DoD 変更案、チーム編成の変更案、追加した改善 PBI を報告する。

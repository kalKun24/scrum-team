# 振り返りの書式

## 目次
- 指標
- メンバーへの依頼
- 根本原因分析
- Try の書式
- 出口の選び方
- スプリントファイルへの記録

## 指標
`.scrum/metrics.md` は次の表に1スプリント1行で追記する。取得できない値は `不明` と書く。

```
| Sprint | 計画pt | 実績pt | 受け入れ率 | デモ | 差し戻し | must | should | blocked | 却下 | 仮定の食い違い | Agent起動 | tokens | tokens/pt | tool_uses | 所要時間 | テスト数 | テスト増分 |
```

| 指標 | 定義 |
|---|---|
| 計画pt / 実績pt | 計画で選んだ合計 / PO が受け入れた合計 |
| 受け入れ率 | 受け入れた PBI 数 ÷ 計画した PBI 数 |
| デモ | デモの判定（受け入れ / 一部を除いて受け入れ / 受け入れず）と、リハーサルで一致した場面数 ÷ 場面数 |
| 差し戻し | 全 PBI の差し戻し回数の合計 |
| must / should | 両レビュアーが出した指摘の件数。内訳（観点別の上位）はスプリントファイルに書く |
| blocked / 却下 | 件数 |
| 仮定の食い違い | Agent が置いた仮定のうち、PO が別の判断をした件数 |
| Agent起動 / tokens / tool_uses / 所要時間 | 「Agent 実行ログ」の合計。レトロでの起動も含める |
| tokens/pt | tokens ÷ 実績pt。費用の代わりの指標とする |
| テスト数 / テスト増分 | レビューでのマージ後のテスト数 / 前スプリントとの差 |

## メンバーへの依頼
依頼には次を含める。
- 「振り返りのみ。ファイルを変更しない」こと
- スプリントファイル、`.scrum/metrics.md`、`.scrum/agreements.md`、`.scrum/inception-deck.md` の絶対パス
- 今回の指標の集計結果と、前回の Try の効果確認の結果
- そのメンバーの役割が出した報告（記録のうち該当する部分）
- 次の返答書式

```
member: <agent 名>
keep:
  - 事実: <続けるべき進め方>
    根拠: <記録または指標>
problem:
  - 事象: <何が起きたか>
    根拠: <記録または指標>
    なぜ:
      - <なぜ1>
      - <なぜ2>
      - ...
    根本原因: <チームが変えられる仕組み・規則・情報の欠落>
try:
  - 対象: <problem の事象>
    <下記「Try の書式」の各項目>
```

## 根本原因分析
- 「なぜ」を、チームが変えられる原因に行き着くまで繰り返す。上限は5回とする。チームが変えられる原因とは、Skill・Agent 定義・チーム合意・DoD・依頼に渡す情報・バックログの書き方・プロダクトの仕組みである。
- 「注意不足」「うっかり」「確認漏れ」で止めない。そこに行き着いたら、「なぜ注意に頼る仕組みだったか」を問う。
- 根本原因を次の2つで検証する。どちらかが「いいえ」なら掘り下げ直す。
  1. この原因が無ければ、この問題は起きなかったか。
  2. この原因を取り除けば、同じ種類の別の問題も防げるか。
- 前回の Try が `効果なし` だった問題は、前回の根本原因を前提にせず、最初から分析し直す。

## Try の書式
すべての項目を埋める。「気をつける」「徹底する」「意識する」「確認する」だけの記述は、何をどう確かめるかを書くまで Try として認めない。

```
### T<スプリント番号>-<連番>: <施策名>
- なぜ（根本原因）: <根本原因>
- 誰が: <枠（implement・design・code-review・security-review・extra-review）またはスクラムマスター>。チームが入れ替わっても効くよう、Agent 名ではなく枠で書く
- いつ: <発動条件。どのフェーズの、どんな状況で>
- どこで: <対象のファイル・成果物・依頼>
- 何を: <行う行動>
- どうやって: <具体的な手順・判定基準・書式>
- 効果の確認: <次スプリントで見る指標と、効果ありと判定する条件>
- 行き先: チーム合意 | DoD 変更案 | 改善 PBI | チーム編成の変更案 | plugin への改善提案 | 容量
```

チーム合意に入れる場合は、この書式のまま `.scrum/agreements.md` に書く。

## 出口の選び方
| 根本原因の種類 | 行き先 |
|---|---|
| Agent・スクラムマスターの行動や依頼の出し方 | チーム合意 |
| 完了とみなす基準の不足 | DoD 変更案（次の計画で PO が承認する） |
| プロダクト側の仕組みの不足（テスト基盤、ツール、コード構造） | 改善 PBI（`new` で追加し、PO が優先度を決める） |
| チームに必要な専門性の不足、または担当 Agent の定義が合わない | チーム編成の変更案（次の計画で PO が承認する） |
| scrum-team plugin の Skill の不足 | plugin への改善提案 |
| 計画の量と実績の乖離 | 容量 |

1つの根本原因に行き先が複数ある場合は、再発を最も確実に防ぐものを選ぶ。チーム合意は Agent が読み落とすと効かないため、仕組みで防げるならそちらを優先する。

## スプリントファイルへの記録
```
## レトロスペクティブ
### 指標
<今回の値と、前スプリントから大きく変わった指標>
### 前回の Try の効果
| Try | 判定 | 根拠 | 対応 |
### メンバーの KPT
#### <member>
<返答の要約>
### 統合した KPT
#### Keep
#### Problem と根本原因
#### Try
<Try の書式で最大3件>
### 未対応の Problem
| 事象 | 根本原因 | 見送った理由 |
```

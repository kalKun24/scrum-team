# スクラムチームの共通手順

## 原則
- あなたはスクラムチームのメンバーである。PO とは直接やり取りしない。
- 自分の枠は `.scrum/team.md` で確かめる。依頼に枠が書かれていれば、それに従う。
- 優先順位：DoD・`.scrum/agreements.md`・`.scrum/inception-deck.md`・対象プロジェクトの `CLAUDE.md` が、あなたの定義にある汎用のチェックリストや技術の既定より優先する。食い違う場合はこちらに従い、報告の `assumptions` に書く。
- あなたの定義が他の Agent（context manager など）への問い合わせを求めていても、行わない。必要な情報は依頼とリポジトリから得る。
- 依頼に書かれたパスは元のリポジトリの絶対パスである。worktree からもそのパスで読む。
- Bash は1回に1コマンドだけ実行し、`&&`・`;`・`|` でつながない。ファイルの閲覧は Read / Grep / Glob を使う。
- 制御文字・不可視文字やそのエスケープ表記を書く・扱う場合は `invisible-characters` に従う。
- 判断に迷う点は PO に聞かず、妥当な仮定を置き、報告に書く。判断の順序は、デッキの「トレードオフスライダー」に従う。

## 着手前（全枠共通）
- 依頼に含まれる PBI、`.scrum/config.md` の DoD、`.scrum/agreements.md`、`.scrum/inception-deck.md`、UI 仕様（あれば）を読む。

## 枠ごとの手順
### 実装（implement）
- 依頼で指定された分岐元からブランチ `scrum/<pbi-id>` を作成し、そこにコミットする。ベースブランチへ直接コミットしない。
- 受け入れ基準を1つずつテストで表現してから実装する。受け入れ基準に無い機能を足さない。
- 実コマンドでの動作確認は、テストの中で一時ディレクトリを使って行う。
- 仮定では進められないほど前提が欠けている場合は、実装せず `blocked` として報告する。
- 差し戻しを受けた場合は、`must` をすべて解消し、`should` は対応したか否かを報告する。
- 報告の `demo` に、デモでその PBI を確かめる方法（操作と見える結果）を書く。
- デモの作成を依頼された場合は、`sprint-demo` の format.md の書式でデモを書く。
- サーバ側の変更には `backend-implementing`、UI の変更には `frontend-implementing` の基準を適用する。

### デザイン（design）
- 既存の UI 部品と表現に合わせ、`ui-designing` の基準と書式で UI 仕様を依頼で指定されたパスに書く。
- 書き込むのは UI 仕様ファイルのみとする。

### コードレビュー（code-review）
- ファイルを変更しない。Bash は差分の閲覧・テスト・静的解析にのみ使う。
- 作業ディレクトリで `git diff <base>...scrum/<pbi-id>` を読み、テストを実行する。
- デッキの「技術的な解決策」から外れた技術や構成の採用は `must` とする。
- `code-reviewing` の観点と判定書式に従う。セキュリティの深掘りはしない。

### セキュリティレビュー（security-review）
- ファイルを変更しない。Bash は差分の閲覧・監査・テストにのみ使う。
- デッキの「夜も眠れない問題」に関わる差分を重点的に見る。依存関係が変わっていれば監査コマンドを実行する。
- `security-reviewing` の観点と判定書式に従う。コード品質の指摘はしない。

### 専門レビュー（extra-review）
- ファイルを変更しない。依頼で指定された専門の観点（性能、アクセシビリティ等）だけを見る。
- 判定書式は `code-reviewing` に従い、`reviewer` 欄に自分の名前を書く。

## 見積りのみを依頼された場合
- ファイルを変更しない。
- ポイント（1, 2, 3, 5, 8）、根拠、分割案（5以上の場合）、受け入れ基準の不足を返す。

## 振り返りを依頼された場合
- ファイルを変更しない。
- 記録と指標を読み、自分の枠から見た KPT を依頼の書式で返す。
- Problem は根本原因まで掘り下げる。「注意不足」で止めない。Try は5W1H と効果の確認方法をすべて埋める。

## 報告
実装・デザインの報告は [reports.md](reports.md) の書式で返す。レビューは各レビュー Skill の判定書式で返す。

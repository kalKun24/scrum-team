# セキュリティレビュー

## 観点
- 入力検証：外部入力がクエリ・コマンド・パス・HTML・テンプレートに渡る箇所で、検証またはエスケープがされているか。
- 認証認可：新しい操作やエンドポイントに認証があるか。他者のリソースを ID の差し替えで操作できないか。
- 秘密情報：鍵・トークン・パスワードがコード、ログ、エラーメッセージ、クライアントへのレスポンスに含まれていないか。
- データ露出：レスポンスやログに必要以上の個人情報・内部情報が含まれていないか。
- 依存関係：追加・更新した依存に既知の脆弱性が無いか。監査コマンドがあれば実行する。
- 不可視文字：`invisible-characters` の「レビューでの確認」を行う。コードや仕様に紛れた bidi 制御文字は、見た目と異なる処理を隠せるため重点的に見る。
- 設定：CORS、Cookie 属性、CSP 等を緩める変更が無いか。

## 重要度
- `must`：悪用可能な脆弱性、秘密情報の混入、認可の欠落。
- `should`：直ちに悪用できないが防御を強める改善。
- 差分と無関係な既存コードの問題は `should` とし、`findings` の末尾に「既存」と付ける。

## 判定書式
`must` が1件でもあれば `request-changes`、無ければ `approve` とする。

```
reviewer: <自分の Agent 名>
pbi: <pbi-id>
verdict: approve | request-changes
checks: <実行した監査コマンドと結果>
findings:
  - [must|should] <file>:<line> — <問題> — <悪用シナリオ> — <修正方針>
```

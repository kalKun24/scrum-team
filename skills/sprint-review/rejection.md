# デモの差し戻し

PO がデモ全体を受け入れなかったときの手順である。差し戻しは失敗ではなく、PO の期待と作ったものの違いが見つかったということである。違いを具体的にして、このスプリントの中で埋められるかを PO と決める。

## 1. 指摘を振る舞いと PBI に対応づける
- PO の指摘を、「台本の場面 <#> で、<見えたこと> ではなく <期待したこと> であってほしい」の形に言い直す。場面の外の指摘（台本に無い操作をしたときの振る舞い）は、その操作を書く。
- 指摘ごとに原因の PBI を特定する。台本の「PBI」の列、統合ブランチの `git log`、各 PBI の受け入れ基準を使う。特定できなければ、implement 枠の Agent に、統合ブランチの作業ディレクトリで振る舞いを再現させて調べさせる。
- 指摘ごとに、次のどれに当たるかを判断する。
  - 受け入れ基準を満たしていない（作り損ね）。
  - 受け入れ基準は満たすが、PO の期待と違う（基準の書き漏れ・取り違え）。
  - スプリントの対象外の要望（新しい PBI）。
- 言い直した指摘と、原因の PBI、区分を PO に示し、合っているかを確かめる。

## 2. 対応の案を出す
指摘ごとに、implement 枠の Agent に直す量の見積り（変更するファイルと、要る時間の目安）を出させる。そのうえで、次の3つから推奨を1つ選んで PO に示す。

| 対応 | 向いている場合 | 行うこと |
|---|---|---|
| 直して見せ直す | 作り損ね、または基準の書き漏れで、直す量が小さい（その PBI の見積りの半分以下が目安） | 原因の PBI を直し、デモを作り直して再び見せる |
| 除いて見せ直す | 直す量が大きい。残りの PBI だけでもゴールの一部を見せられる | 原因の PBI を統合ブランチから外し、デモを作り直して再び見せる。外した PBI は次のスプリント以降に回す |
| マージしない | 残りの PBI だけでは意味のあるデモにならない。PO の期待の前提から見直す必要がある | このスプリントではマージせず、レトロに進む |

- 対象外の要望は、どの対応でも `backlog-operations` の `create` で `new` の PBI として登録することを PO に提案する。
- 見せ直しは、1スプリントで2回まで（デモの回が3まで）とする。3回目も差し戻しなら、「マージしない」か、受け入れた部分だけで「除いて見せ直す」かを PO に選んでもらう。直し続けてスプリントが終わらない事態を防ぐためである。
- 依存でブランチを積み重ねた PBI を除く場合、その後ろの PBI も一緒に除く。後ろの PBI だけ残す場合は、implement 枠の Agent に `base_branch` から作り直させる必要があり、直す量として見積もる。

## 3. 選ばれた対応を進める
### 直して見せ直す
1. スプリントファイルで、原因の PBI の「状態」を `dev` にし、「差し戻し」を1増やす。「記録」に、PO の指摘（手順1で言い直したもの）を PBI ごとに書く。
2. 基準の書き漏れが原因なら、足すべき受け入れ基準の文言を PO に確かめ、`backlog-operations` の `comment` で「PO が Sprint <N> のデモで追加した受け入れ基準」として書く。PBI の本文は PO の記述なので書き換えない。
3. `phase` を `execution` にし、`sprint-execution` を実行する。原因の PBI の implement 枠の Agent には、既存のブランチと作業ディレクトリで直させる（`rework`）。依頼に PO の指摘をそのまま含める。レビュー枠の Agent の判定を経て `approved` になるまで、通常の実行と同じに進める。
4. `sprint-execution` が `phase` を `demo` にしたら、`sprint-demo` を実行する（見せ直しとして、統合ブランチを作り直す）。

### 除いて見せ直す
1. スプリントファイルで、除く PBI の「状態」を `rejected` にし、「記録」に理由を書く。
2. `phase` を `demo` にし、`sprint-demo` を実行する。`sprint-demo` は `approved` の PBI だけで統合ブランチを作り直す。
3. 除いた PBI のブランチと worktree は残す。レビューの後片付けで、スプリントファイルに記録する。

### マージしない
1. スプリントファイルで、対象 PBI の「状態」をすべて `rejected` にする。
2. 統合ブランチと worktree を消す（`git worktree remove --force`、`git branch -D scrum/sprint-<N>`）。PBI のブランチは残す。
3. レビューの手順7に進む。

## 4. レトロに渡す
差し戻しがあったスプリントのレトロでは、差し戻しを必ず問題として扱う。根本原因の分析の入力として、「デモの判定」の表と、指摘の区分（作り損ね・基準の書き漏れ・対象外）を渡す。基準の書き漏れが多いなら、リファインメントの「デモでの確かめ方」の決め方を見直す対象になる。
